## 1. 产品概述

### 1.1 一句话定位

**Create characters. Discover their stories.**

EchoLoom 是角色驱动的互动创作工具。用户先用自然语言创造角色和形象，再围绕这些角色开始故事，通过对话、选择、导演指令与改写探索不同发展，保存喜欢的故事线，形成可继续加工的小说或剧本草稿。

### 1.2 产品要解决的问题

1. 用户有一个人物想法，但填写完整档案和另外生成头像的流程过长。
2. 人物设定完成后，用户需要一个清楚的“开始故事”动作。
3. 创作者希望试出人物之间的冲突和对白，同时能随时修改，不被迫接受一次生成。
4. 尝试另一种发展时，不应丢掉原来的故事线。
5. 离开、刷新、修改角色后，创作者需要知道哪些内容已保存、继续的是哪个版本。
6. 探索结果应能导出，进入后续写作流程。

### 1.3 目标用户

- 有人物想法、希望用互动探索剧情的业余创作者。
- 需要试演对白、冲突和转折的小说、剧本或互动叙事创作者。
- 喜欢角色互动、希望把一次体验整理成故事草稿的用户。

### 1.4 本期目标

让用户在一个手机原型中完成：

> 我描述一个人物 → 他和头像一起出现 → 我调整细节 → 我开始一个故事 → 我推动和改写剧情 → 我保存一条喜欢的 Storyline → 下次回来继续或导出。

主要验证角色到故事的转化是否自然、创作过程是否可控、故事线能否被理解与找回。生成字数、连续签到与强迫使用时长不作为成功标准。

## 2. 产品原则

1. **延续原流程。** 角色创建仍是主要入口，不先要求建立一个复杂项目。
2. **描述优先。** 用户先写想法，系统完成初稿，再允许逐步调整。
3. **一次创建，包含形象。** 头像生成属于 Create character 的默认流程，不要求用户另找一个按钮。
4. **创作者有控制权。** 可以自由输入、代写台词、调整方向、保存不同发展。
5. **保存可理解。** 自动保存防止丢失；命名保存帮助找回；分支用于尝试不同发展，三者不混为一谈。
6. **短界面，完整能力。** 每屏突出主要操作，设置和说明渐进展开。
7. **真实呈现状态。** 生成中、部分成功、失败、未保存和演示模式均明确显示。
8. **人物和故事连续。** 不串角色、不串故事线、不用新设定静默覆盖旧稿。

## 3. 关键概念

| 名称 | 产品含义 | 用户在哪里看到 |
| --- | --- | --- |
| Character | 可反复使用的人物，包含设定、角色版本和头像版本 | Characters、角色详情 |
| Story | 一部作品／一次完整故事的容器，包含标题、前提、角色、背景和故事线 | Stories、Story overview |
| Storyline | 同一个 Story 中的一条剧情发展路径 | 故事内的 `Main`、`Version B` 等选择器 |
| Scene | Storyline 中按顺序发生的一场戏，包含时间、地点、参与者和当下目标 | 故事阅读器、场景列表 |
| Moment | 每次生成或手工写入的一个短片段，包含若干旁白、动作和对白 | 阅读器中的片段与编辑操作 |
| Saved version | 给某条 Storyline 当前状态做的命名快照，不随之后的编辑变化 | `Saved versions` |
| Story facts / Canon | 作者确认的设定、事件和角色知情信息，带范围与来源 | Story 的 Notes 页面 |

**层级关系：Story → Storyline → Scenes → Moments。**

- 一个角色可以出现在多个 Story 中；每个故事使用明确的角色快照。
- 创建 Story 后默认就有一条 `Main` Storyline，不要求用户先学会“分支”。
- 自动保存后仍在同一条 Storyline 上继续。
- `Save storyline` 创建一个命名保存点，不自动复制出新的发展路线。
- `Try another version` 才会分出新的 Storyline，保留原路线。
- 初期不把 Project 作为首次使用的概念；未来长篇项目可以建立在 Story 上，不阻塞当前流程。

## 4. 用户流程与导航

### 4.1 首次使用主流程

1. 打开首页，看到产品定位与 `Create character`。
2. 输入一段角色描述，点击一次创建。
3. 系统生成角色档案，并自动生成匹配的头像。
4. 用户看到人物预览，可以直接 `Start a story`，也可以先编辑设定、改头像。
5. 输入故事开场，选择参与方式和出场角色。
6. 直接进入故事阅读器，看到第一段互动。
7. 用户继续、选择方向、写自己的台词或改写一个片段。
8. 系统自动保存；用户可 `Save storyline` 命名当前版本。
9. 如想比较另一种发展，使用 `Try another version`。
10. 返回 Stories 找到作品，继续上次的位置或导出当前故事线。

不要求先创建项目、填写全部字段、先普通聊天或连接日历。

### 4.2 老用户流程

- 已有角色：Characters → 角色详情 → Start a story。
- 已有故事：首页 Continue / Stories → 恢复上次的 Storyline、场景和阅读位置。
- 已有保存点：Story → Saved versions → 只读预览 → Continue from here，建立可编辑的新 Storyline。
- 想为现有故事增加另一个角色：先创建／选择人物，再明确应用于新场景或新故事线，不把第三位说话者突然插入当前场景。

### 4.3 导航结构

底部主导航三项：`Home`、`Characters`、`Stories`。

- Home：创建入口、最近故事、最近角色、一个可体验的示例。
- Characters：全局角色库，创建、查看、编辑和归档。
- Stories：作品列表、筛选、继续、归档与删除。
- Story 内部：Overview、Scenes、Storylines、Notes；在概览页用卡片／分段入口呈现，不再叠加一整排底部导航。
- 阅读器：顶部返回 Story、标题、当前 Storyline 和更多菜单；底部集中推进、输入与保存。

故事线和命名保存点都在所属 Story 内管理，避免额外建立一个内容重复的全局 Saved 页。

## 5. MVP 范围与优先级

### 5.1 P0 必须交付

| 模块 | 要求 |
| --- | --- |
| 一键人物创建 | 一段描述触发角色档案和头像生成；支持分别失败与恢复 |
| 人物调整 | 编辑档案、自然语言局部修改、头像重生成／局部修改、选择旧头像版本 |
| 开始 Story | 从人物直接进入；自动命名可编辑；不强制先建 Project |
| 两种参与方式 | 用户扮演一个角色；或导演两名 AI 角色 |
| 互动阅读 | 短片段、继续、建议意图、自由输入、阅读位置恢复 |
| 创作控制 | 编辑台词／叙述、改变方向、重写最新片段 |
| Storyline | Main 自动建立、分叉、命名、切换、移动端比较 |
| 保存与恢复 | 自动保存、命名保存点、继续写、保存状态反馈 |
| 基础连续性 | 当前分支上下文、角色快照、手工确认事实、来源追溯 |
| 导出 | 当前 Storyline 的小说／剧本 Markdown、复制、JSON 结构备份 |
| 移动体验 | 393×852 基准、键盘和安全区适配、清晰状态与错误恢复 |

### 5.2 P1 后续增强

- 更完整的 AI 事实提取、冲突提示和角色知识分析。
- 三名以上同场角色、复杂关系图、可视化大型故事树。
- 长篇章节规划、跨多个场景的更高级上下文管理。
- 图片上传、场景插图生成、多种成套美术风格。
- 包含图片文件的完整便携导出包、PDF／DOCX。
- 云端跨设备同步、协作、作品公开分享与权限体系。

### 5.3 本期不包含

恋爱数值、约会匹配、日历同步、主动生活提醒、特殊人群活动、语音／视频对话、原生 App、付费和社交社区。

上述功能不出现在新的 Creator 主流程中。现有陪伴模式的记录和已授权功能保持原样，不在本轮被清空或改名覆盖。

## 6. 功能规格：人物创建与调整

### FR-C01 — 输入描述

创建页主要只有：

- 标题 `Who would you like to create?`
- 多行描述框，必填，1–5,000 字符。
- 一个简短示例，可一键填入。
- 主按钮 `Create character`。

描述可以包括外貌、性格、背景、目标、说话方式、人物关系。字段没有全部出现也允许创建；用户不必先填写表格。

默认使用与参考一致的二维插画方向，可在折叠设置里查看；不把一串画风参数放在首次创建首屏。

### FR-C02 — 同一次操作生成角色与头像

点击创建后：

1. 立即保存描述草稿和本次 requestId。
2. 生成并校验角色档案。
3. 从已校验的外貌与原始明确描述形成头像提示，自动发起图像生成。
4. 展示人物预览，头像完成后显示并选为本次人物的初始头像。

这是**用户感知的一次创建动作**；内部可分阶段完成，不要求两个 provider 请求成为一个全有或全无的事务。

- 明确输入的姓名、外貌和背景不能无故改变。
- AI 补充内容属于可编辑人物初稿。用户未提供的关键历史、秘密不应直接被写成不可变事实。
- 头像要与已生成外貌一致；描述修改后应基于当前版本，而不是旧提示。
- 创建成功后直接展示人物，不再要求用户重新点击 Generate portrait。
- 图像接口未配置时，要明确说明头像未生成，不能用未标注的库存图冒充结果。

### FR-C03 — 生成状态与部分成功

界面只显示短状态，例如 `Creating character…`、`Creating portrait…`，不显示无依据的假进度百分比。

| 档案状态 | 头像状态 | 产品行为 |
| --- | --- | --- |
| 生成中 | 未开始 | 保留描述，显示创建状态，可停止等待 |
| 成功 | 生成中 | 先显示人物信息、头像占位和状态；可开始编辑 |
| 成功 | 成功 | 显示人物与头像，主操作 Start a story |
| 成功 | 失败／未配置 | 保留人物，显示 Retry portrait；允许无头像开始故事 |
| 失败 | 未开始 | 保留描述，提供 Retry，不调用无依据的图像生成 |

档案可用时不因头像慢而丢失人物。允许先开始 Story：故事记录初始角色快照及对应的待完成头像任务；该初始任务成功可一次性补齐对应的初始形象，不改故事文本。后续另一次头像修改不得静默覆盖该 Story 的形象。

停止等待不保证上游计费请求已经取消。迟到结果只能归入原创建任务，不能覆盖更新后的角色或另一位角色。

### FR-C04 — 人物预览与编辑

预览显示：头像、姓名、一句话身份、核心性格、目标、说话方式。详细背景在折叠区。

主要操作：`Start a story`、`Edit character`；头像上有清楚的编辑入口。

角色字段：

| 字段 | 限制／规则 |
| --- | --- |
| Name | 1–60 字符；档案生成后应有可编辑名称 |
| Short description | 最多 160 字符 |
| Appearance | 年龄描述、头发、眼睛、衣着等，可留空 |
| Personality | 核心性格、价值观、行为倾向 |
| Wants | 当前目标，最多 300 字符；开 Story 时可补充／覆盖 |
| Why it matters | 动机与利害，最多 500 字符 |
| Fear / boundary | 最多 300 字符 |
| Voice | 语气、词汇与说话习惯，最多 300 字符 |
| Background | 最多 1,500 字符；允许未知 |
| Private information | 最多 500 字符；不代表所有其他人物均知道 |

支持直接编辑和自然语言调整，例如 `Make her more reserved, but keep her background and appearance.`。

自然语言修改先显示简短差异预览，再由 `Apply changes` 确认；只改相关字段，不整体重建人物。不要求每个字段单独确认。

### FR-C05 — 头像调整

支持两种操作：

- `Try another portrait`：基于当前外貌重新生成一个候选。
- `Edit portrait`：用户输入局部指令，如改变发色，向图像编辑接口提交当前源图。

候选生成后先预览，用户选择 `Use this portrait` 才替换当前选择；原图保留在历史中，可以切回。

头像修改不自动改变人物性格和背景。修改发色后的图像若与档案外貌不一致，提供简短的 `Update appearance too`，仅在确认后更新相应字段，不能让图像结果反向改写整个档案。

正在生成旧头像时若用户已手动选择另一版本，旧请求完成不得抢回选中状态。重试图像失败只重试图像，不重新生成档案。沿用后端图像额度与频率限制，避免失败后无界自动重试。

### FR-C06 — 人物保存与故事引用

有效档案与图像各自成功后保存，显示对应的真实状态。直接编辑字段通过 Save；生成调整通过 Apply changes 保存为新修订。

角色库是可复用的“母版”；Story 的角色快照不随母版被动变化。

- 旧 Story 默认继续旧快照。
- 用户主动 `Use updated character` 时，预览差异。已有正文的 Story 应从当前节点建立新 Storyline，供后续使用更新设定；旧路线和保存点保留。
- 只想试一个人物的另一种性格，可复制为新角色，不覆盖原角色。
- 角色或头像已被 Story 引用时，默认允许归档；不能直接删除仍被引用的资产而让历史故事损坏。

## 7. 功能规格：开始与管理 Story

### FR-S01 — Start a story 入口

人物详情的主按钮为 `Start a story`。首页和 Stories 也提供同一入口，后两者先选择至少一位已有角色。

点击后保留已选角色，填写：

1. `What happens first?`：开场情境，1–1,000 字符，必填。
2. `How would you like to write?`：参与方式。
3. 另一个参与者／角色，随方式出现。

故事标题可根据开场建议，稍后改名；不作为开始前的必填表单。时间、地点、氛围、世界规则和边界收在 `Scene details` 中。

### FR-S02 — 两种参与方式

**Play a role**：延续原来“我和角色发生故事”的方式。用户可以使用简短姓名和身份，不必先创建完整的第二份档案；自己的关键选择和台词由自己决定。

**Direct the cast**：选择两名已有角色，由 AI 演出两者，用户作为导演控制剧情。没有第二角色时，可以继续创建，已有的开场草稿必须保留。

MVP 每场最多两名说话角色，包括用户扮演的角色。可以提到未出场人物，但不能无提示地把第三位人物加入说话者。

两种方式都使用同一套 Story、Storyline、保存、分叉与导出能力。模式标识始终可查看。改变参与方式应新建 Storyline 或 Story，不静默改写已有用户台词的作者身份。

### FR-S03 — 生成并进入第一场戏

点击 `Begin story` 后：

- 先保存 Story 设置、角色快照与初始 `Main` Storyline。
- 进入阅读器，显示第一段生成状态。
- 成功后保存第一 Moment，并展示正文。
- 失败保留 Story 与设置，显示 Retry opening，不要求重新填表。

不再用“发送邀请卡再点 Begin”作为创作者必经流程。原陪伴聊天中的故事卡仍可保留在原模式。

### FR-S04 — Story overview

显示标题、封面、故事前提、角色、当前 Storyline、最近场景和进度。

主要操作 `Continue story`，其余入口：Scenes、Storylines、Saved versions、Notes、Export。

Stories 列表可以按最近更新、进行中、已完成／归档筛选。无需创建 Project 才能管理一个 Story。

### FR-S05 — 多场景与结束

单个 Storyline 可以按顺序添加多个 Scene。每场至少包含一个 Moment。

`New scene` 提供新的时间、地点、开场和场景目标，默认继承当前 Storyline 的有效事实与人物快照。不能把其他路线的结果带入新场景。

MVP 保证示例中至少两场戏能够连续写作；不自动排出整本书的章节结构。

`Finish story` 是作者的明确操作，可填写结尾或生成短结尾后确认。标记完成不等于禁止阅读、导出或再探索；继续探索时建立新的 Storyline，保留已完成版本。归档只从默认列表收起，不删除内容。

## 8. 功能规格：互动创作阅读器

### FR-R01 — 阅读与布局

顶部显示 Story 标题、当前 Storyline、返回和更多菜单；正文显示场景标题、参与者、旁白、动作与对白。

每次生成约 4–6 个 blocks，通常 100–220 个英文单词，不自动连续生成整章。支持 Next 和 Show all；不默认自动播放。

底部显示两项主要操作与自由输入，其他功能渐进展开：

```text
← Story          The Last Train          ⋯
Scene 1 · Main                         Saved

[场景背景／角色呈现]
Leo      “A one-way ticket?”
Mira     “You weren't supposed to be here.”

[Continue]             [Save storyline]
[Direct the scene or write a line…      ↑]
```

用户上翻时，新内容不能强制拉回底部；显示 `New moment ↓`。返回、刷新后恢复阅读位置和未发送草稿。

### FR-R02 — 继续、建议与自由输入

- Continue：根据当前角色、关系、目标和有效上下文，继续一个片段。
- 建议意图：最多三条，例如 Let Mira deflect、Let Leo ask more gently。
- 自由输入：可输入方向、角色台词或动作；可以明确选择作者操作类型。

在 Play a role 下，建议只表达意图，不自动替用户承诺、原谅、告白或做重大行动。用户已写的台词原文保留。

在 Direct the cast 下，用户可以让任一出场角色说话、修改其行为或要求某种冲突发展。系统应结合角色动机回应；若指令有意改变既定设定，应提供明确的分支方式。

### FR-R03 — 改变方向

例如 `Turn this into a quiet study session instead of searching the shelves.`。

该操作影响当前路线接下来的发展，不默认修改母版角色。保留指令原文，以便理解路线如何形成。

可以使用新 Moment 推进；如要替换已生成但不满意的内容，应使用 Rewrite 或从相应节点分叉，不悄悄删除已保存的前文。

### FR-R04 — 编辑与重写

- Edit this moment：打开底部编辑面板，修改对白、说话者、动作或旁白。
- Rewrite moment：输入要求，只重写最新片段，保留原版本以便恢复。
- 人工内容带轻量 `Your edit` 标记，模型草稿带 `AI draft` 标记。

编辑没有后续的最新 Moment，创建可恢复修订。编辑已有后续的历史 Moment，从其之前的共享前缀创建新 Storyline，以修改后的 Moment 接续；原路线与后续不变。

若改写改变了来源事实，关联 Notes 标为 Needs review。AI 不能无提示地改写同一路线的所有历史。

### FR-R05 — 生成、取消与重试

- 同一 Storyline 同时只允许一个生成操作，重复提交按 requestId 去重。
- 成功校验并持久化后才追加新 Moment。
- 失败保留旧正文、输入、阅读位置和重试信息，不保存半截“成功”。
- 停止等待、切换 Storyline 或退出后，迟到结果不能进入另一个路线。
- 错误信息不包含密钥、完整 provider 原始响应或其他用户内容。

## 9. 功能规格：自动保存、保存点与继续

### FR-P01 — 自动保存

Story 设置、成功生成的片段、人工编辑、阅读位置、分支选择应自动持久化；输入草稿可先保存在设备本地。

状态使用 `Saving…`、`Saved`、`Couldn't save · Retry`。只有真实持久化完成才显示 Saved。

- 自动保存不要求用户反复点击 Save storyline。
- 正文未保存时离开应提示，或清楚说明本地草稿仍在；不能悄悄丢弃。
- 恢复后不会重新请求同一段内容，避免重复计费和重复追加。

### FR-P02 — Save storyline

用户希望明确留住一个节点时使用。

1. 点击 Save storyline。
2. 底部小面板提供默认名称，例如 `Before the departure`，可编辑。
3. 保存当前路线有效路径、当前 Scene、角色／设定快照和相关事实状态。
4. 完成后出现短反馈 `Version saved`，留在原界面继续。

命名保存点是固定快照。之后继续写不会覆盖它；不同名称可保存多个点。对同一个保存请求重试不产生重复快照。

保存按钮不是后台自动保存的替代品，也不是创建新 Storyline 的隐式入口。

### FR-P03 — 恢复与继续写

- Continue story：恢复最近有效 Storyline 和阅读位置，直接在其末端继续。
- 打开保存点：先只读预览当时内容。
- Continue from here：从保存点创建新的可编辑 Storyline，名称可修改；保存点本身不改变。
- 原来的 Main 和其他路线仍在，删除恢复出的路线不会删除保存点。

保存点不重复调用模型来“恢复”旧内容。历史文本必须与保存时一致。

## 10. 功能规格：Storyline 分支与比较

### FR-B01 — Try another version

从指定 Moment 的结尾分叉，输入另一种发展意图。MVP 不支持任意单词处的分叉。

- 新路线默认名 Version B、Version C，可改名。
- 分叉前的前缀共享但只读；分叉后的片段、编辑和事实属于各自路线。
- 新生成失败时不丢旧路线；新路线可以保留为待重试草稿。
- 主观上更喜欢 B 时，只需选择 Use this storyline，不必删除 A。

### FR-B02 — 路线列表与比较

每条路线显示名称、来源节点、最近更新、简短预览和状态。

手机上使用 A/B 切换阅读与相同锚点的内容比较；不把两列长文字挤进 393 px，也不在 P0 做大型节点图。

切换不重新生成，不合并两条路线的记忆或角色知情状态。删除、归档前清楚说明范围。

### FR-B03 — 与 Scenes 和保存点的关系

- 在 Scene 1 分叉，新路线不能继承原路线 Scene 2 的内容，除非它位于分叉前的共享路径。
- 从历史节点分叉后，可以用 New scene 写新的 Scene 2。
- 保存点保留对应路线在当时的完整有效路径。
- 被其他路线或保存点引用的节点不能级联删除；后台可在无引用后回收。

## 11. 功能规格：连续性与故事事实

Notes 页面分为：

1. Story setup：作者确认的背景、世界规则和角色快照。
2. This storyline：此路线中的事件、知情信息与来源。
3. Suggested updates：待作者审核的提议。

### FR-N01 — 确认与来源

每条事实包含：内容、适用范围、知情角色、来源 Moment／作者输入、状态。

P0 支持手动添加、编辑、确认、撤销和删除；可演示一条结构化 AI 建议。AI 提议默认 Suggested，不能自动升级为 Confirmed。

片段在当前草稿中已发生的事件，可用于本路线的临时续写上下文；这不等于它成为其他路线或其他 Story 的事实。

### FR-N02 — 知识隔离

- 角色的秘密只有作者和设定中知道的人知道；另一个角色应在实际披露后才可能知情。
- Version B 的坦白不能改变 Main 中角色的知识。
- 母版角色在另一部 Story 中发生的事件，不会自动带入当前作品。
- 内容来源被替换或移出有效路径，相关事实标为 Needs review。
- 与确认设定明显冲突时提示 `This changes a confirmed detail`，允许修改指令或另试路线，不静默重写世界观。

MVP 不宣称完美的语义一致性、自动理解所有秘密或无限长期记忆。确定性隔离、结构校验和一组人工评审案例均为验收要求。

## 13. 贯穿 MVP 的演示故事

### 13.1 第一段：描述并生成角色

用户输入：

> Mira is a reserved young restorer with short dark hair and a quiet, precise way of speaking. She wants to leave her hometown for a residency, but finds it difficult to explain that choice to her younger brother.

一次创建得到人物档案与头像。用户把说话方式调整为“更克制、偶尔带一点干幽默”，修改头像细节并选择版本，然后直接点击 Start a story。

### 13.2 第二段：开始 Story

提供两种可体验路径：

- Play a role：用户扮演弟弟 Leo，以简短姓名和身份加入。
- Direct the cast：使用预置或创建的 Leo，由用户导演双方。

场景：雨夜站台，末班车 23:10 出发。Leo 看见 Mira 的单程票，但不知道驻留机会。

Mira 想按计划离开又避免解释全部原因；Leo 想得到说明，又不愿显得在恳求。没有人被设定为必然原谅、留下或告白。

### 13.3 第三段：保存并探索另一种发展

1. 进入 Main，Leo 发问，Mira 回避。
2. 用户输入方向：让 Leo 更平静地追问，避免变成争吵。
3. Save storyline，命名 `A quiet confrontation`。
4. 从发问处 Try another version，让 Mira 坦白驻留机会。
5. 手工修改一句台词，比较两个版本。
6. 在新路线中确认“Leo 得知驻留机会”，回到 Main 后该事实不得出现。
7. New scene，在新路线中继续下一场戏。
8. 导出选中 Storyline 的剧本稿，退出、刷新、重新打开后恢复。

这段演示必须体现：一键人物与形象生成、调整、开始故事、连续互动、命名保存、分支差异及恢复，不能只展示静态页面跳转。

## 14. 导出、备份与数据管理

### FR-E01 — 文稿导出

- Prose draft：旁白、动作与对白按有效路径输出。
- Script draft：场景标题、角色名、对白与舞台动作。
- 先预览，再复制或下载 `.md`；可选择当前 Scene 或整个当前 Storyline。
- 不包含被替换的片段、未选路线的后续或仅供模型使用的秘密提示。
- 导出草稿不等于自动确认全部内容为 Canon。
- 剪贴板权限不足时显示可手工选取文本；下载不支持时提供复制备选。

### FR-E02 — JSON 结构备份

P0 JSON 包含 Story、角色／设定快照、关系、全部 Storyline、保存点、片段、事实来源、schemaVersion；不包含密钥和诊断日志。

图片以资产引用与校验信息保存。JSON 不是包含图片二进制的完整素材包；同一后端仍有素材时可以恢复引用，素材缺失时保留文本并显示图片占位。包含图片文件的便携包列为 P1，不能把当前 JSON 描述成完整图片备份。

导入先校验格式、引用关系、版本与大小（P0 上限 5 MiB，不含图片二进制），预览后追加为独立 Story；重映射内部 ID，不覆盖当前角色母版或其他 Story。

### FR-E03 — 删除与归档

- 角色归档：不再默认供新故事选择，已有快照继续可用。
- Story 归档：从默认列表收起，能够恢复。
- 删除 Story：明确会移除其路线和命名保存点，不删除仍被其他 Story 使用的母版角色与图片。
- 删除路线或保存点：只影响选定对象，不删除其他对象仍引用的前缀。
- 删除有二次确认，普通编辑与保存不重复要求确认。

## 15. 视觉、文案与移动端设计

### 15.1 视觉方向

参考 `Zhguo903/Echoloom` 的设计 tokens、样式与预览图：明亮、留白、纸感、柔和卡片、人物肖像与视觉小说式叙事。

使用**象牙白创作页面 + 插画式场景画布**。夜景可局部使用深靛氛围，但文字和操作区保持稳定清晰；不做完整深浅主题切换，也不沿用 V2 大面积紫色作为新模式的主视觉。

| Token | 色值 | 用途 |
| --- | --- | --- |
| Slate | `#586580` | 品牌、导航 |
| Deep slate | `#344056` | 标题、深色操作 |
| Champagne | `#C8B28D` | 重要操作、路线节点 |
| Sage | `#789787` | 连续性、确认与保存 |
| Ivory | `#FBF8F1` | 页面背景 |
| Paper | `#FFFDF8` | 卡片、编辑面板 |
| Charcoal | `#283241` | 正文 |

标题和人物名使用 Georgia／系统衬线 fallback，正文与表单使用系统无衬线。常规正文 15–16 px，辅助文字至少 12 px，主标题约 26–32 px。圆角约 17–22 px，克制的阴影和细描边。

按钮／正文对比度逐项验证，常规文字目标至少 4.5:1、大号文字至少 3:1；香槟色并不天然适合白字，可改用深色文字或更深的按钮色。可点击目标至少 44×44 px，主按钮约 50 px 高。状态不只依赖颜色。

### 15.2 移动端要求

- 基准 393×852，同时验证 360、390、430 px 宽度。
- 手机浏览器全宽展示，尊重安全区和动态视口；不叠加假系统状态栏。
- 桌面仅需居中手机宽度预览，不增加左右仪表盘。
- 软键盘弹出时输入和发送可见；输入框增长有上限，正文仍可查看。
- 页面无横向溢出，A/B 对比采用切换阅读。
- 底部导航不遮挡列表，阅读器工具栏不遮挡最后一段。
- 支持返回手势／浏览器后退、焦点恢复、减少动画偏好。

### 15.3 文案规范

UI 和默认示例采用英文；本 PRD 使用中文说明。用户输入的名字、设定和对白原文保留，不自动翻译。生成语言显式继承 Story 的语言，本期首先支持 English。

关键 CTA：Create character、Start a story、Continue、Save storyline、Try another version、Continue from here、Export。

首屏一条短说明足够。没有默认展开的长教程、成功说明弹窗或重复产品介绍。生成成功直接进入人物或故事，保存成功用短反馈。

## 16. 系统、数据与非功能要求

### 16.1 实现策略

优先复用现有 Next.js、FastAPI、角色档案／画像 provider 和持久化基础；Creator 使用独立业务入口与故事实体。

- 真实角色、头像和创作记录以现有后端数据库及资产目录为主要来源，新增实体按迁移保存。
- 本地存储用于未提交输入、阅读缓存与恢复标识，不把“只有浏览器临时状态”当作已保存作品。
- 与服务端断开时显示 `Saved on this device · Waiting to sync` 或未保存状态，恢复后使用 requestId 和版本号合并，不能盲目覆盖更新内容。
- Demo 数据使用独立命名空间与明确模式标识，不能覆盖真实创作记录。
- 本期不承诺跨设备云同步；手机真机验收需要可访问的同源预览地址及对应后端，不能把电脑的 127.0.0.1 当成手机可访问地址。

### 16.2 关键实体

Character、CharacterRevision、PortraitVersion、CharacterCreationJob、Story、StoryCastSnapshot、Storyline、Scene、MomentRevision、SavedVersion、StoryFact、GenerationRequest。

需要记录创建／更新时间、版本号、资源归属、来源 requestId、有效路径与引用关系。文本和图片生成任务各自记录成功状态，以支持部分成功与单独重试。

现有单角色 StoryOutput 不直接等于双角色导演模式；需有严格的角色 ID／说话者契约。不能仅改前端标签就宣称已支持多人互动。

### 16.3 上下文与安全

生成只读取当前 Storyline 的有效路径、角色快照、作者确认约束和有来源的草稿摘要。上下文超预算时保留约束、目标、重要选择与最近片段，摘要不能覆盖正文。

后端密钥不进入浏览器。已有账户的权限检查继续适用，新 Story、图片和保存点均需绑定同一数据归属；没有账户时只能按既有受信本地单用户模式工作，不宣称公开多用户隔离。

模型输出结构化校验，用户文本安全渲染。provider 拒绝或错误使用固定、安全说明；不得泄露原始密钥、隐私上下文或其他用户内容。

### 16.4 性能与可靠性目标

- 用户点击后约 300 ms 内出现明确的可见反馈；不要求模型在 300 ms 内生成完毕。
- 网络及设备正常时，页面内普通操作不阻塞整个应用；长生成可以离开后恢复状态。
- 图像和文本超时分别处理，复用合理的服务端 timeout 与限额；重试有次数／退避策略，不无限后台请求。
- 已保存内容刷新后无需再次生成即可读取；保存点恢复不得重复调用模型。
- 可记录真实模型延迟，不使用虚假秒数或固定假进度掩盖等待。
- 数据迁移前保留可恢复路径；原有 `.env`、数据库和图像资产不清空。

### 16.5 真实生成与演示模式

Live AI 是自定义描述生成角色／头像、自由导演指令和双角色推演的真实能力路径。核心实现验收必须验证调用、状态、保存及恢复；有权限模型的实测结果另外记录。

可同时提供无需密钥的 Try an example：使用预置人物、图片和有区别的故事路线，编辑、保存、分叉和导出仍真实工作。全程显示简短 Demo mode 标识。任意自由输入若超出演示支持范围，应保留输入并说明需要 Live AI，不用通用套话冒充推演。

用户进入真实创建流程但服务未配置时，提示可打开示例或完成服务端配置；不能悄悄把预置图片当作其描述生成的头像。真实生成失败也不能无提示地切换到演示输出。

## 17. 异常与边界验收

| 情况 | 要求 |
| --- | --- |
| 档案成功、头像失败 | 人物保留；只重试头像；可开始 Story |
| 图像生成期间修改人物／换头像 | 旧请求不覆盖新选择，按版本与任务关联保存 |
| 重复点击 Create / Begin / Continue / Save | 同 requestId 不创建重复角色、片段或保存点 |
| 有效回复返回但保存失败 | 不显示 Saved；保留可恢复结果，重试保存不再次生成 |
| 生成期间切换 Storyline | 迟到响应不写入另一条路线 |
| 刷新时任务未完成 | 查询原任务／结果状态，不盲目重新发起付费请求 |
| 修改被 Story 引用的角色／图片 | 历史快照和保存点保持稳定，更新需明确作用范围 |
| 编辑有后续的片段 | 创建另一条路线，原后续保留 |
| 分叉后新增场景 | 只继承本路线的前文与事实 |
| 删除共享内容 | 仍有引用的节点或图片不能级联删除 |
| 图片服务未配置或拒绝 | 明确失败状态，不用未标注预置图冒充真实生成 |
| 输入／导入不合法 | 定位错误并保留已填内容，原记录不变 |
| 剪贴板／下载不支持 | 提供预览和替代导出方式 |
| 存储、网络或认证失效 | 明确未保存状态和恢复步骤，不静默丢失或跨账户写入 |

## 18. 验收标准

| 编号 | 验收结果 |

| AC01 | 首次使用可从描述直接创建人物，不强制先创建 Project |

## 19. 事件记录与产品验证

为评估创作流程，记录以下最小事件：character_create_started、profile_ready、portrait_ready／failed、story_started、moment_generated、direction_submitted、storyline_forked、saved_version_created、story_resumed、export_completed。

只记录操作标识、模式、耗时和结果等必要信息；不默认把用户完整小说、秘密、聊天内容或 provider key 发送到分析系统。原型阶段可先使用本地／服务端诊断记录，不强制接第三方埋点。

形成性试用建议约 5 位目标创作者，任务如下：

1. 输入描述，得到一个人物与头像，调整一处特征。
2. 开始 Story，推进至少两轮互动。
3. 保存一条 Storyline，再探索另一种发展。
4. 比较、返回、继续并导出。

初步目标：至少 4/5 能在少量或无需口头指导下完成主流程；多数人能区分自动保存、命名保存点与分支；收集至少一个愿意继续加工的场景及具体原因。小样本用于发现问题，不作为普遍有效性的证明。

必查质量问题：人物行为是否可信、头像是否匹配描述、路线是否有真实差异、秘密是否无故泄露、用户是否知道内容保存在何处。
