## 1. 产品定位

**Create characters. Discover their stories.**

先创造人物，再通过人物之间的互动发现故事。创作者设定人物想要什么、害怕什么、彼此如何看待对方，将他们放进一个有张力的场景，探索不同的发展，再选择值得继续写下去的版本。

本期用户身份是创作者／导演，可以控制所有出场角色；也可以直接替一个角色写台词。首次使用不要求用户以恋爱对象或故事中的玩家身份出现。

首页辅助文案：

> Build a cast. Explore their choices. Shape what happens next.

### 1.1 要验证的核心假设

1. 先明确角色目标、矛盾与关系，能否帮助创作者得到更有用、可继续加工的场景？
2. 创作者是否能在手机上容易地推进互动、改写一个片段，并比较另一种发展？
3. 探索结果能否成为可带走的草稿，同时让创作者理解哪些是设定、哪些只是尝试中的内容？

本期验证创作流程的价值，不以生成长篇小说的字数或停留时长作为成功标准。

### 1.2 目标用户与主要场景

- 小说／短篇创作者：探索人物冲突、对白与关键转折。
- 剧本／互动叙事创作者：试演一场戏，比较不同选择的后果。
- 有角色设定、尚未找到剧情切入点的业余创作者。

典型使用时刻：有两个角色和一个冲突，想用 5–10 分钟试出一场值得继续写的戏。

## 2. MVP 边界

### 2.1 P0：本期必须体现的闭环

**打开示例或新建项目 → 建立两个人物与关系 → 设置一场戏 → 推进互动 → 输入导演指令／编辑对白 → 保存另一种发展 → 比较 → 确认一条故事事实 → 导出选中版本。**

| 模块 | P0 范围 | 本期边界 |
| --- | --- | --- |
| Projects | 示例项目、新建、重命名、继续、删除 | 本地个人创作，不做团队协作 |
| Cast | 创建与编辑人物、目标、动机、底线、声音；人物关系 | 项目可有 2–6 个角色；单场戏最多 2 个说话角色 |
| Scene | 地点、当下情境、出场角色、各自目标 | 一次生成一个短片段，不自动生成整章 |
| Explore | 继续、自由导演指令、修改片段中的对白／叙述 | 默认导演视角；不自动扮演用户做重大选择 |
| Versions | 从片段边界分出新版本、命名、切换、比较 | 用版本卡片／列表呈现，不做复杂节点地图 |
| Canon | 人工确认故事事实、标注知情角色、查看来源 | 事实受版本约束；AI 提议不能自动升级为正式事实 |
| Export | 当前版本的小说稿／剧本稿 Markdown、复制；项目 JSON 备份／导入 | 不做 DOCX、PDF 排版或出版工具 |
| Persistence | 刷新、返回、关闭后继续；错误恢复 | 本期创作者原型数据保存在同一浏览器，不承诺跨设备同步 |

### 2.2 本期不包含

- 恋爱数值、约会发现、签到、付费货币、排行榜。
- 日历、日常主动关心、通知和特殊人群活动机制。
- 语音通话、配音、角色口型或视频生成。
- 三人及以上的同场多人对话、无限自动推进、长篇自动成书。
- 自动理解并记住整个项目的一切信息。
- 原生 iOS／Android 应用、应用商店发布、多人编辑和公开作品社区。

这些限制只约束新的 Creator 模式，不删除或迁移现有陪伴模式、聊天、日历和历史记录。

### 2.3 原型的两种运行模式

**Demo mode：** 无需账号或 API key 即可打开预置项目，实际执行选择、导演指令的预设路线、编辑、分支、确认和导出。状态变化、保存及分支隔离必须真实工作。页内用简短 `Demo mode` 标识说明内容由预设演示生成；详情放在设置中。

- 演示情境必须有至少三条有区别的内容路径。
- 自由输入始终可以输入和保存。只有支持的预设意图可以获得演示续写；不支持的意图保留原文，并提示 `This direction needs live AI. Your draft is saved.`，提供编辑草稿或切换 Live AI 的操作。
- 自建项目可保存角色、场景和手工片段；无模型时不能伪装成理解任意设定并完成真实推演。

**Live AI：** 复用既有后端文本 provider，接收结构化场景上下文并返回片段；服务器保管密钥，浏览器不输入或存储 provider key。已配置模型时，用同一套前端操作自由探索。未配置或服务失败时保留原稿并说明状态，不静默切成预设回复。

本期先交付完整 Demo 路径和真实数据操作，并保留／接通文本生成适配层。真实模型的完整验收需要有权限的模型配置；模拟测试通过与实测通过应分别记录。

## 3. 首次体验与信息架构

### 3.1 首次体验

首次打开不播放长剧情序章，不要求做性格测试或填写完整世界观。

首页展示定位、一个可直接进入的示例和 `New project`。用户选择示例后，直接看到两个人物的矛盾与 `Explore the scene`，约 2 次点击进入第一场戏。

新建项目采用渐进流程：项目名称 → 两个人物 → 开场情境。只把必填项放在当前步骤，其他设定后续补充。

### 3.2 导航

- 顶层 `Projects`：项目卡片、最近编辑时间、示例、新建。
- 进入项目后使用四项底部导航：`Overview`、`Cast`、`Scenes`、`Canon`。
- 所有项目内页面保留当前项目名；返回项目列表不会重置内容。
- 沉浸式场景工作台隐藏项目底部导航；顶部 `Back to scenes`，底部保留推进与导演操作。
- 导出放在场景／版本的更多菜单中，不占一项主导航。

这是针对创作者重新组织的导航；视觉上继承参考仓库，不照搬其关系成长、EchoLink 或任务结构。

## 4. 页面规格

### P01 — Projects

主要元素：EchoLoom 品牌、主标题 `Create characters. Discover their stories.`、短副标题、`New project`、`Try an example`、项目卡片。

项目卡片显示封面、标题、两个人物头像、最近场景和更新时间。点击卡片进入项目 Overview；若已有草稿，优先显示 `Continue scene`。

空状态只提供一个明确动作，不叠加功能介绍。删除项目需二次确认，确认中说明会删除该项目内人物、场景和版本，不影响其他项目。

### P02 — Project Overview

- 项目标题与一句话 premise；封面为静态原创背景。
- 最近场景卡片及 `Continue scene`。
- 人物关系摘要：谁想要什么、冲突在哪里。
- `Explore a new scene`。
- 可折叠 `World rules`，放作者明确输入的背景、限制和已确认全局设定。

本页服务“我接下来写哪一场”，不堆叠统计仪表盘。

### P03 — Cast / Character

角色卡片显示头像、姓名、一句话身份、当前目标。点击进入编辑，字段如下。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| Name | 是 | 1–60 字符 |
| Role / one-line description | 否 | 最多 160 字符 |
| Wants | 是 | 当前想得到什么，最多 300 字符 |
| Why it matters | 否 | 动机、代价，最多 500 字符 |
| Fear / boundary | 否 | 恐惧或不愿越过的线，最多 300 字符 |
| Voice | 否 | 说话方式与习惯，最多 300 字符 |
| Background | 否 | 最多 1,500 字符；未知可留空 |
| Private information | 否 | 作者已设定、其他角色未必知道的信息，最多 500 字符 |

首屏只显示姓名、身份、目标；其余放入 `More about this character`。头像可从原创预置图中选择；新的图片生成流程和自定义上传不是本期关键路径。

关系编辑以 A→B 和 B→A 分开保存：怎么看对方、想从对方得到什么、主要矛盾。可使用文字，不使用单一好感度分数。未知保持未知，不自动补成事实。

保存角色时创建版本。已生成的场景保留其角色快照；角色修改不会改写旧场景。继续旧场景前如有新设定，可选择 `Keep scene setup` 或 `Use updated characters`；采用更新则形成新的场景版本并检查明显冲突。

### P04 — Scene Setup

可从空白创建，或点击示例情境。

首屏必填：

1. 两个出场角色。
2. `What is happening?`：开场情境，最多 1,000 字符。
3. 两个角色此刻的目标：默认取角色目标，可对本场单独覆盖。

可选展开项：地点与时间、氛围、必须遵守的边界。场景名可自动建议，但能编辑。

主操作 `Explore the scene`。点击后立即进入场景页并显示生成状态；无需再通过一个成功弹窗进入。

自建场景尚无片段且未配置模型时，显示 `Write first moment`，使用同一片段编辑器手工建立草稿；不能只有一个不可用的生成按钮。

MVP 默认外部镜头视角，呈现可见动作和对话。作者的秘密可影响人物行为，但不应仅因模型知道秘密，就让另一个角色无故知情。

### P05 — Scene Studio（核心）

这是视觉与交互的重点。参考视觉小说的场景画布和角色呈现，同时让创作者能迅速操作。

屏幕结构：

```text
← Scenes       The Last Train       ⋯
[场景插画／氛围背景，适量角色肖像]
Scene 1 · Main version · Draft

雨中的站台……
Leo      “A one-way ticket?”
Mira     “You weren't supposed to be here.”
Leo      “Were you going to tell me?”

[Continue]      [Try another version]
[Direct the scene…                 ↑]
```

- 一次生成约 4–6 个 blocks，通常 100–220 个英文单词；不把整章塞进一个回复。
- block 类型只有旁白、动作、对白；对白明确标注说话者。
- 支持逐段阅读和 `Show all`；默认不开自动播放。暂停或退出不丢进度。
- 新片段在末尾出现。创作者向上阅读时不强行拉回底部；提供 `New moment ↓`。
- 默认固定主操作不超过两个，自由输入入口始终可见。更多设置、导出和场景信息收在菜单中。
- 建议方向最多 3 条，必须是意图，例如 `Let Leo press for an answer`，不是替创作者写好唯一允许的完整对白。自由输入与建议具有同等地位。

#### F05.1 Continue

按当前有效版本、人物目标、关系、已知信息和最近片段继续。一次点击只生成一个片段。不自动创建未经作者设定的重要背景或第三位说话者。

#### F05.2 Direct the scene

作者输入方向，例如：`Let Mira avoid the question, but show that she is nervous.`

系统保留指令原文，并生成下一片段。指令只作用于当前场景版本；不会直接修改角色全局性格或世界设定。

#### F05.3 Edit this moment

点击片段的编辑操作，打开底部编辑面板。可以编辑某一条对白、动作或旁白，修改说话者时只能选择已出场角色。空白内容不能保存。

- 编辑尚无后续的最新片段：保存修订，保留可恢复的原文本。
- 编辑已有后续的历史片段：明确提示 `Continue from this edit in a new version`，从被编辑片段之前的共同前缀新建版本，以修订后的片段接续；原分支及其后续内容保留。
- 重新生成最新片段采用同样的修订逻辑，失败时原片段保持可读。

人工写入的台词标为 `Your edit`；模型生成内容标为 `AI draft`；界面可用轻量标记，不能只靠颜色区别。

#### F05.4 Keep this moment

将片段标记为创作者希望保留的草稿内容，可取消保留。这个动作不会自动把模型推断写成全项目事实。

若有新的故事事实提议，只出现一个简短 `Review story updates` 入口，作者可稍后到 Canon 审核，不弹出长篇解释或阻断阅读。

#### F05.5 生成中与失败

显示 `Exploring…`，允许停止等待。停止后保留指令和旧稿；迟到结果不得写入已经切换的版本。

失败显示短错误及 `Retry`；保留输入、滚动位置和旧稿。不把部分返回或预设替代回复保存成成功结果。

同一版本一次只有一个生成操作。移动端重复点击和网络重试必须通过 request ID 去重；生成完成与保存成功后，才算产生了一个新片段。

### P06 — Versions / Compare

主入口 `Try another version`，位于片段末端或版本菜单。

- 选择从哪个已存在片段的结尾分叉；第一版不支持任意字词处的分叉。
- 输入新的发展意图，可接受一个自动建议名称。
- 新版本共享分叉前的只读前缀，拥有独立的后续内容、阅读进度和故事更新。
- 默认命名 `Main`、`Version B` 等，作者可以改名。当前版本名始终可见。
- P0 不做深层树形地图；使用版本列表加来源说明，例如 `From Main · Moment 2`。

比较页在手机上用 A／B 切换和同一锚点的连续阅读，不将两列小字硬塞进 393 px。显示共有开场、分叉方向和不同的后续，允许 `Use this version` 返回选中的草稿。

`Use this version` 只选择当前编辑／导出路径，不删除另一版本，不把它的事实迁入本版本，也不自动将所有生成内容确认为正式设定。

删除版本需确认；至少保留一条有效路径。被其他版本引用的共享片段不得级联删除，可将旧版本归档而保留前缀引用。

### P07 — Canon

给创作者一个可理解的“本故事目前确认了什么”的页面。

分两组：

1. `World & character facts`：作者输入并确认的全局设定。
2. `This version`：当前版本已确认的事件与角色知情状态。

每条记录有：文字、适用范围、知情角色、来源片段／作者输入、确认状态。可以编辑、撤销确认或删除。

- AI 提议默认为 `Suggested`；只有作者确认后变为 `Confirmed`。
- 草稿中新发生的事情可以作为当前分支的临时上下文继续写，但不能跨分支、跨项目成为正式事实。
- 用户未填写秘密或动机时，系统不能用推断替代已确认设定。
- 版本 A 中的坦白不影响版本 B 的人物知情状态。
- 来源片段被改写或移出有效路径时，关联事实标为 `Needs review`，不继续当作无条件成立的依据。
- 如新指令明显冲突，提示 `This changes a confirmed detail`，提供修改指令或从此处试另一个版本；不静默重写设定。

P0 必须支持手动添加、确认和查看来源。AI 自动提议可在 Demo 中演示一条，在 Live 模式按结构化输出接入；复杂自动矛盾检测属于后续增强，不承诺识别所有语义冲突。

### P08 — Export & Backup

从当前场景菜单或版本比较页进入。

- `Prose draft`：按有效路径输出旁白、动作和对白。
- `Script draft`：按场景标题、角色名、对白和舞台动作输出。
- 先预览，再选择复制或下载 `.md`；默认只导出当前版本的有效内容，不拼入其他版本或被替换稿。
- 导出当前草稿不等于确认全部事实；该区别在格式说明中用一句话表达。
- `Project backup (.json)` 包含项目、角色版本、关系、场景、全部分支、事实来源、阅读进度和 schemaVersion。
- 导入先校验结构与大小（P0 上限 5 MiB，不包含内嵌图片），提供预览和确认；创建新的项目 ID，不覆盖已有项目。错误文件不改变现有数据。
- 剪贴板受限时显示可选择文本供手工复制。移动浏览器不支持下载时，提供复制备选，不显示虚假成功提示。

## 5. 必须可完成的演示故事

### 5.1 示例项目：The Last Train

两个成年姐弟在雨夜站台相遇，时间接近末班车。

| 人物 | 目标 | 动机／矛盾 | 私有信息／知情边界 |
| --- | --- | --- | --- |
| Mira | 按计划离开，又不愿解释全部原因 | 想接受另一座城市的修复师驻留机会，同时害怕让弟弟觉得被抛下 | 知道自己获得了驻留机会；开场时尚未告诉 Leo |
| Leo | 在列车出发前得到一个解释 | 把姐姐的离开理解为上次争吵的结果，又不愿显得在恳求 | 看到单程票，但不知道驻留机会 |

作者确认：末班车 23:10 出发。开场时两人关系紧张，但没有人被预设为必然道歉、原谅或留下。

### 5.2 约五分钟演示路径

1. 打开示例，查看两人的目标与关系。
2. 进入场景，读到 Leo 发现单程票并发问。
3. 在 Main 中选择 `Let Mira deflect`，继续一段含蓄而紧张的对话。
4. 输入导演指令：`Make Leo ask more quietly. He wants an explanation, not a fight.`，看到对白与节奏变化。
5. 从发问片段另建 Version B：`Let Mira admit the residency offer.`。
6. 看到另一种发展；Leo 此时才可能知道这个信息。
7. 手动改一条台词，让表达更符合作者想法。
8. 比较两个版本，选择 Version B 继续。
9. 在 Canon 确认“在此版本中，Leo 得知驻留机会”，检查来源片段；切回 Main，不应出现这条事实。
10. 导出 Version B 的剧本草稿，再返回后继续原来的进度。

两条版本需要有可见的行为与后果差异，不能只换几个同义词。

## 6. 视觉与移动端交互要求

### 6.1 参考依据与继承方式

已核对参考仓库的 `app/styles.css`、`docs/design-tokens.json`、`docs/DESIGN_SYSTEM.md` 以及预览图。参考同时包含明亮的纸感页面和深靛色叙事氛围扩展；预览图与部分文档反映不同迭代阶段。

本期采用：**明亮纸感的创作页面 + 插画式、可阅读的叙事画布**。场景可以使用局部深靛／夜景背景，但文字和控制区保持稳定、清晰。第一版不做一套完整的深浅主题切换。

不沿用 V2 当前大面积淡紫色作为主视觉。也不照搬参考项目的剧情、人物身份、扫描开场、恋爱关系数值或导航结构。

### 6.2 设计 tokens

| 用途 | 颜色 |
| --- | --- |
| Slate / 主品牌、导航 | `#586580` |
| Deep slate / 标题 | `#344056` |
| Champagne / 主操作、重要版本节点 | `#C8B28D` |
| Muted sage / 保留、连续性、确认状态 | `#789787` |
| Ivory / 页面底色 | `#FBF8F1` |
| Paper / 卡片、编辑面板 | `#FFFDF8` |
| Charcoal / 正文 | `#283241` |

色彩使用参考 token 的家族，不代表所有组合都可直接用。按钮、正文、占位文案和插画叠层须单独检查对比度；重要文字优先深色，必要时用更深的香槟色或石板色按钮。

- 标题与人物名：Georgia／系统衬线 fallback。
- 正文、对白、表单：系统无衬线字体；不依赖外部字体服务。
- 常规字号 15–16 px，辅助文字至少 12 px，主要标题约 26–32 px。
- 卡片圆角 17–22 px，面板最大 28 px；柔和阴影、细描边与克制的半透明层。
- 主按钮高度约 50 px，所有可点击目标至少 44 × 44 px。
- 角色卡强调肖像、目标和矛盾；避免把长档案表格直接铺满首页。

### 6.3 画幅与适配

- 基准 393 × 852；必须同时验证 360、390、430 px 宽度。
- 桌面展示为居中的手机宽度预览；不要求使用手机外壳，也不增加桌面左右仪表盘。
- 真正手机上全宽展示，使用动态视口高度并尊重安全区，不在真实浏览器重复画假系统状态栏。
- 键盘弹出后，导演输入框和发送按钮仍可见；输入框自动增长但不遮住全部正文。
- 横向无溢出；版本比较改用切换阅读。
- 顶栏和底栏稳定，内容区域独立滚动，底部操作区不盖住最后一段内容。
- 页面返回、浏览器后退与恢复后，保存当前版本、阅读位置和未发送输入。

### 6.4 视觉小说感的具体来源

使用场景氛围图、人物肖像、叙述与对白的层次、章节标题和留白建立叙事感。编辑和分支操作使用一致的底部面板／短菜单。每屏只有一个主要任务，不用长解释代替可操作的控件。

图片须为原创、已授权或明确可使用的素材。参考仓库是风格依据，不自动构成复制其全部素材的授权。

## 7. 内容与生成规则

1. 角色的目标、声音、关系和可知信息必须进入当前场景上下文。
2. 输入优先级：系统边界 → 作者确认设定 → 当前版本有效片段与人工修订 → 本次导演指令 → 未确认建议。
3. 明确区分事实冲突与作者有意改变故事；必要时要求选择新版本，不擅自修正作者。
4. 人物可以拒绝、回避、误解和改变策略，但应有当前动机支持。
5. 不把戏剧性等同于每轮新增秘密、事故、告白或突然出现的新人物。
6. 模型输出只允许结构化 block、说话者和可选更新提议；不接收任意 HTML。
7. 模型生成不保证绝对一致。除自动校验外，必须用预设冲突案例进行人工评审，并保留编辑／重试能力。
8. UI 与默认示例为英文。作者自己输入的名称、设定和对白不自动翻译或改写；输出语言显式继承当前项目设置，本期先支持 English。

## 8. 数据与状态约定

### 8.1 最小实体

| 实体 | 关键内容 |
| --- | --- |
| Project | id、标题、premise、世界规则、语言、当前场景、schemaVersion |
| CharacterRevision | characterId、版本、设定字段、头像引用 |
| Relationship | A/B 角色、两个方向的态度／诉求／矛盾 |
| Scene | projectId、参与者、开场、场景目标、角色／世界快照 |
| SceneVersion | id、来源版本、分叉片段、名称、当前有效 head、阅读位置 |
| MomentRevision | id、parent、blocks、来源指令、作者编辑标记、保留状态 |
| StoryFact | 内容、范围、知情角色、来源片段、建议／确认／待复核状态 |
| GenerationRequest | requestId、目标版本、expectedRevision、状态、结果引用 |

场景片段及修订按不可变记录保留，由版本指向有效路径。列表与比较界面可以简单，但底层不能通过覆盖一份字符串假装有分支。

### 8.2 上下文范围

生成只使用当前项目与选中版本的有效路径。上下文预算不足时使用明确标记的摘要和最近片段，同时保留作者确认约束、角色目标与重要选择。其他项目、其他分支和被放弃的候选不得混入。

旧场景的快照与后来角色版本不能静默混用。摘要是派生内容，不能覆盖来源正文。

### 8.3 本期保存策略

Creator 原型优先使用独立命名空间的 IndexedDB 保存创作项目和草稿；JSON 备份作为可带走的副本。既有 V2 的数据库、角色、画像和聊天不迁移、不清空。

Live AI 可使用现有后端 provider 适配层，但本期不因此承诺云端项目同步。涉及模型请求时，应显示模式与状态，并沿用后端鉴权和服务端密钥规则。

若浏览器储存不可用或容量不足，明确提示 `Changes aren't saved on this device`，保留内存中的草稿并提供导出。不能在失败后仍显示 Saved。

应用升级需按 schemaVersion 迁移，并在导入／迁移失败时保留旧副本。清空浏览器数据会影响本地项目，这一说明放在项目设置和备份入口。

## 9. 异常、边界与恢复

| 情况 | 必须发生的行为 |
| --- | --- |
| 未配置 Live AI | 可进入完整预置 Demo；自建情境不能显示假的实时 AI 成功 |
| 网络中断／模型超时／格式错误 | 保留旧稿、输入和当前位置，提供重试；不产生半个成功片段 |
| 快速连点／重复网络请求 | 同 requestId 返回已有结果，不重复追加 |
| 生成中切换版本或退出 | 不向新版本追加旧请求结果；回到原版本可看到其明确状态 |
| 编辑已有后续的片段 | 新建修订版本，保留原路径及后续 |
| 删除人物 | 若被场景引用，允许归档或要求先处理引用；不破坏旧场景快照 |
| 删除共享分支 | 保留被引用的前缀；不能让其他版本失效 |
| 事实来源被替换 | 标为 Needs review，停止无条件作为确认依据 |
| 空项目／仅一个角色 | 保留已填内容，引导补齐第二角色再开场 |
| 导出失败／剪贴板受限 | 保留预览，提供复制／下载的另一条路径 |
| 存储失败／导入错误 | 不覆盖原数据，不显示虚假保存成功 |

## 10. 验收标准

| 编号 | 可检查的验收结果 |
| --- | --- |
| AC01 | 无 API key 也能打开示例，完成至少一次方向调整、分叉、比较、事实确认和导出；界面标明 Demo mode |
| AC02 | 可新建项目，创建两个人物并保存不同目标与关系；刷新后存在 |
| AC03 | 角色与场景的非必填信息可保持未知，不自动变成既定事实 |
| AC04 | 场景生成后直接进入可读工作台，最多两个说话角色，支持自由输入 |
| AC05 | Continue 一次只追加一个成功保存的短片段；重复请求不重复追加 |
| AC06 | 导演指令对当前版本产生可见变化，不偷偷修改全局角色档案 |
| AC07 | 人工改写最新对白可保存；编辑历史片段产生新版本并保留原路径 |
| AC08 | 从同一节点可得到有意义差异的两个版本；切换与比较不丢输入或阅读位置 |
| AC09 | Version B 的驻留机会披露不会让 Main 的 Leo 自动知情 |
| AC10 | Canon 可确认／撤销／查看来源；被替换来源标 Needs review |
| AC11 | 导出的小说稿／剧本稿只来自选定版本，角色名、顺序与可见正文一致 |
| AC12 | JSON 导出后可导入为独立项目；原项目不被覆盖，结构错误文件被拒绝 |
| AC13 | 生成失败不丢旧稿，切换页面后的迟到响应不污染另一个版本 |
| AC14 | 393×852、360 与 430 px 宽度均无横向溢出；手机键盘不挡住输入和提交 |
| AC15 | 移动端前进／后退、刷新和重新打开可恢复同一浏览器内的内容与进度 |
| AC16 | UI 使用确认的参考色彩与字体层次；正文可读、触控目标≥44 px，关键信息不只靠颜色 |
| AC17 | 预置演示、自建项目未配置模型、Live AI 三种实际状态可辨认，不静默冒充生成能力 |
| AC18 | 原角色陪伴、历史聊天、画像、剧情和日历的数据与现有入口仍可用 |

Live AI 实测补充验收：使用有权限的真实文本模型完成自建两角色情境、自由导演指令和改写；记录角色一致性、知识边界、生成延迟、失败恢复与成本。该项未实测时必须标为待验证，不能以预置 Demo 或 mock 测试代替。

## 11. 验证方法与成功信号

先做约 5 位目标创作者的形成性可用性试用，关注问题发现，不将小样本转成疗效或普遍优越性结论。

任务：打开示例 → 描述两人的矛盾 → 改一次方向 → 创建另一个版本 → 选一个版本 → 导出可继续加工的文本。

初步设计目标：

- 至少 4/5 能在少量或无需口头指导下完成核心任务。
- 多数参与者能说明两个版本的区别，并正确辨认哪条事实只属于某个版本。
- 记录是否存在至少一个参与者愿意保留并继续加工的场景，以及具体原因；不以正向回答数替代内容质量分析。
- 所有观察到的数据丢失、串分支、秘密无故泄露和无法恢复问题都进入缺陷清单。
- Live 模式另测人物行为可信度与草稿可用性；Demo 模式主要验证交互理解和操作流程。

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |

| M3 真实生成与体验验证 | 接入现有文本 provider、失败恢复、创作者试用与修订 | 分别给出 Demo 验收、真实模型验证和未解决问题 |

不在本 PRD 中承诺具体发布日期。先完成一个高质量、可验证的移动创作闭环，再考虑更多角色、跨场景长篇记忆、复杂关系网络、插图生成或语音。

## 13. 开发约束与兼容策略

- 在 `Echoloom_V2` 中建立独立 Creator 入口与存储命名空间；本轮不改动参考仓库。
- 优先复用已有 Next.js／FastAPI、结构化输出、provider 边界及故事操作经验；不能假定当前单角色 StoryOutput 直接支持双角色，需要新的严格说话者／角色 ID 契约。
- 参考仓库的纯 HTML/CSS/JS 实现不是本项目必须迁移过去的技术要求。本 PRD 采用的是其视觉语言与移动尺度。
- 不把现有聊天消息、日历推断或旧故事自动导入新项目的正式设定。
- 新模式不能清空 `.env`、现有数据库或画像目录，也不能将密钥送入客户端。
- 原型不宣称生产多用户能力；公开部署、云端保存、跨设备同步和更完整账号恢复另行设计。
- PRD 获得确认后才开始本轮实现；在此之前只交付文档，不修改线上产品文案或覆盖现有产品路线。
