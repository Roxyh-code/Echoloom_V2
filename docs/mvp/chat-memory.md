# Character Chat long-term memory (optional)

Character Chat now supports its own opt-in Mem0 long-term memory. This is
**independent** of the existing Rehearsal experiment. No code or files are
generated by this feature when CHAT_MEMORY_ENABLED=false (the default).

## Local setup

1. Back up `work/` and `.env` with the backend stopped. Use a **separate
   benchmark database** if you do not want test characters mixed with real ones.
2. Install the optional dependency in the virtual environment that launches the
   backend:

   ```powershell
   .\.venv-memory\Scripts\python.exe -m pip install -e ".[dev,memory]"
   ```

3. Add these lines to your **local .env**, not to GitHub:

   ```dotenv
   CHAT_MEMORY_ENABLED=true
   CHAT_MEMORY_DIRECTORY=work/chat-memory
   CHAT_MEMORY_CONTEXT_BYTES=2400
   CHAT_MEMORY_BACKFILL_LIMIT=50
   ```

4. Keep the existing `MEMORY_*` model settings and `LLM_API_KEY`. Restart the
   backend using `\.venv-memory`. No database migration is required.
   `MEMORY_ENABLED` controls Rehearsal only.

## Behavior

- Scope: one account + one character; all conversations with this character
  share memory. Different characters/users never share a Mem0 scope.
- Input: only committed human-user messages, not assistant text, calendar
  content, deleted conversations, character profile text, or story branches.
- Write: asynchronous, deduplicated by original message ID; user messages
  are saved normally even if Mem0 fails. On newly enabled installations, the
  most recent `CHAT_MEMORY_BACKFILL_LIMIT` user messages are queued
  progressively when a chat turn is sent.
- Read: relevant Mem0 extracts are inserted as **untrusted data** within
  `CHAT_MEMORY_CONTEXT_BYTES`, only if the chat context budget has room.
  Current profile, calendar and most recent user message remain authoritative.
- A request can fall back silently to ordinary chat when memory is not yet
  indexed, times out or fails. See `GET /api/characters/{id}/memory/status`
  (authenticated to the character's owner) for ready/pending/failed counts.
- Deleting a character queues removal of that character's Mem0 scope.
  This does not delete other characters' memories.
- Database messages and the Mem0 journal/vector store are separate. Keep the
  complete `CHAT_MEMORY_DIRECTORY` with backups; do not add it to Git.
  Use a single backend worker for local Qdrant.

The memory is **not** a guaranteed faithful, exhaustive transcript; Mem0
may conflate facts or miss details. Particularly sensitive details must be
handled outside of this prototype until a fuller user memory/privacy control
and deletion policy is designed.

## A/B Test

Run in the same backend environment, with only `CHAT_MEMORY_ENABLED`
changed and backend restarted between runs. Use fresh test characters
for each arm and the **same model, prompts, and script**.

Mem0 OFF:

```powershell
py -3.12 .\tests\benchmarks\memory\run_benchmark.py --mode chat --label chat_memory_off
```

Mem0 ON:

```powershell
py -3.12 .\tests\benchmarks\memory\run_benchmark.py --mode chat --label chat_memory_on --wait-for-chat-memory
```

The new wait option checks the character's committed message index before
scoring to avoid a false "forgetting" conclusion while the index is still
running. Compare **condition=fresh** answers across the two runs, not results
from different Rehearsal/Chat modules. Treat keyword scores as preliminary
only; inspect original answers, especially temporal conflicts and negation.

## Offline regression checks

```powershell
.\.venv-memory\Scripts\python.exe -m pytest -q tests/mvp/test_chat_memory.py
```

The mock tests do not spend API credits and cannot validate the real Mem0
model's extraction quality.
