## 2. 产品目标

让用户用一句场景描述，与自己创建的角色共同经历一段可以参与的故事。AI 负责旁白、双方日常台词和小动作；影响用户立场、关系或主要走向的决定留给用户。

核心体验：创建并调整角色 → 进入与该角色的聊天 → 输入框旁「＋」→「一起做点什么」→ 描述双方场景 →「发起邀请」→ 当前聊天出现场景卡片 → 点击卡片进入 → 生成并逐句播放剧情 → 重要节点由用户选择 → 后续剧情回应选择 → 保存、退出、从原卡片继续。

用户无需逐句扮演自己，也不会被系统替自己完成重大决定。

## 3. MVP 范围

### 必须完成（P0）

- 从已有角色进入剧情模式；一个用户角色加一个已创建角色。
- 用文字设置场景，选填关系背景、氛围与用户在故事里的名字。
- 分段生成旁白、角色台词、AI 代写的用户台词与动作。
- 对话气泡逐条展示；支持立即显示本段全部内容。
- 每段结束显示继续入口或决策卡；决策卡支持 2–3 个不同意图与自由输入。
- 阅读过程中可随时暂停并输入台词、动作或剧情方向。
- 最新一段可以重写；决策后可以撤回最近一次决定。
- 自动保存、剧情列表、恢复阅读、结束故事。
- 聊天时间线显示关联场景卡片；剧情正文与普通聊天文本及长期记忆隔离。
- 模型输出校验、失败重试、重复提交保护和多窗口冲突处理。

### 后续（P1）

语音播放、场景背景、更多段落的编辑与分支浏览、显式选择聊天记忆作为开场背景、剧情导出。

### 本版不包含

视频、实时通话、多主要角色群戏、复杂数值养成、完整分支树 UI、每句单独调用模型、自动把虚构剧情写入日常聊天记忆。

## 4. 用户入口与创建流程

唯一主要创建入口放在与已有角色的聊天页面：输入框旁「＋」打开附加功能面板，选择「一起做点什么」。不新增与 Chat 并列的 Stories 标签，不要求用户离开聊天寻找故事栏目，也不要求先聊天一定轮数。先调好角色是推荐使用顺序，不设置完成度门槛。

采用日常社交措辞，但仍保留当前应用对虚构 AI 角色的说明；不宣称角色为真实人类，不伪造角色接受邀请的回复。

| 位置 | 中文语义 | 当前英文界面文案 |
| --- | --- | --- |
| 输入框附加功能 | 一起做点什么 | Do something together |
| 场景表单标题 | 想和 {name} 一起做什么？ | What would you like to do with {name}? |
| 提交按钮 | 发起邀请 | Send invitation |
| 未开始卡片按钮 | 开始 | Begin |
| 已开始卡片按钮 | 继续 | Continue |
| 已结束卡片按钮 | 回顾 | Revisit |

点击入口打开桌面弹窗 / 手机底部面板，顶部保留当前角色头像和名字。场景输入框自动聚焦；关闭后留在同一聊天、同一滚动位置，未提交草稿按 conversation_id 在本地暂存。Esc 和关闭按钮可退出，焦点返回原入口。新角色无头像时使用已有字母头像，不阻塞流程。

创建表单：

| 字段 | 规则 |
| --- | --- |
| 场景描述 | 必填，最多 2,000 字符；包含时间、地点、事件均可，不要求结构化填写 |
| 我在故事里的名字 | 选填；默认现有用户显示名，否则“你” |
| 双方关系 | 选填，最多 500 字符；默认从本次角色设定中可确认的信息提取，不凭空设定恋爱关系 |
| 氛围 | 选填，如日常、温柔、悬疑、冒险；默认跟随描述 |
| 不希望出现的内容 | 折叠选填，最多 500 字符，作为整个故事持续约束 |

提交按钮为“发起邀请”（Send invitation），不是“生成剧情”或“一起写故事”。首次说明：“AI 会代写日常对话，重要决定由你来选；你也可以随时接话或调整剧情。”

沿用当前英文界面与视觉样式，不引入新的设计体系。新增剧情、选项和错误信息使用英文，与现有应用规则保持一致；中文场景输入可以理解，但不改变输出语言。保留已有角色中的原名，不翻译或改写旧数据。

创建时保存角色资料快照及头像引用，避免后续修改角色使旧剧情突然改变。本版不自动同步角色更新；新故事使用最新资料。

### 4.1 发起邀请后必须生成聊天卡片

提交后不自动进入阅读器。服务端在一个数据库事务中创建 Story、角色快照和关联当前 Conversation 的场景卡片事件；成功返回后，表单关闭，卡片出现在当前聊天时间线的当前位置。第一阶段不调用模型，只保存场景；无文字 API 凭据时也能创建卡片。

卡片立即可用：首行显示场景类型图标与角色名，标题使用用户描述的确定性短摘录（去除换行、最多 40 个可见字符并省略），正文显示原描述预览（最多 120 个可见字符），按钮为 Begin。完整原文保存在 Story，不截断。首段成功生成后可用模型生成的短标题更新同一张卡片；标题失败不影响正文。

卡片是中性的应用事件，不冒充角色发言，不显示“TA 已接受”等虚构确认。邀请是否被角色接受及如何发展，由符合角色设定的剧情呈现。用户场景描述中明确给定的故事前提可以直接作为开场背景。

每个卡片固定关联 story_id、character_id、conversation_id，只属于发起时的那个聊天会话。切换会话不搬移卡片；再次查看原会话仍能找到。重复提交同一 request_id 只生成一张卡片；相同描述由用户再次明确发起可创建不同故事。

### 4.2 点击卡片才生成第一段

Begin 打开独立阅读器。若 Story 尚未生成内容，客户端提交一次幂等 start action，显示准备状态；服务端按创建时角色快照、用户场景与约束生成首段。成功后自动逐句展示，不要求用户再点击第二个“生成”按钮。

首段必须在开头落实用户描述的地点、关系和事件；不输出创作建议、故事大纲或“你可以这样写”。角色语气使用 Profile 中的 personality、speech_style、backstory 与 interaction_preferences；不随机换人或重建角色。场景设定与角色核心存在明显冲突时，保留角色核心并先澄清，不静默改变人物。

首段失败时卡片与场景保持存在，阅读器显示 Retry。Retry 复用原请求 ID；生成期间重复打开不能生成多个首段。已有首段则读取记录，不再次调用 start。

### 4.3 从卡片恢复和回到聊天

卡片显示服务端真实状态：未开始 / 准备中 / 进行中 / 等待选择 / 已结束，以及对应 Begin / Continue / Revisit。生成失败使用独立错误标记，不把失败误标为已结束。状态属于同一 story_id，续写不向聊天插入新卡片。

阅读器顶部始终有 Back to chat，返回原 conversation_id、原卡片附近的位置；不强制回默认会话。退出停止播放，不自动结束故事，也不无限后台续写。下次点卡片恢复已保存的内容、逐句位置和未决选择。已完成故事只读回顾；新邀请通过聊天「＋」发起。

可在「＋」面板放次要的 Past activities 入口列出本会话卡片，方便长聊天查找；它不取代聊天卡片，也不形成顶层并列栏目。若单独删除故事，保留原卡片为“已删除”且禁用打开，避免悬空链接；删除角色则全部级联清理。

## 5. 剧情阅读与推进

每段建议 6–12 个内容块、英文约 120–250 词，作为质量目标而非严格字数校验。优先短台词、可见动作、少量旁白，每段推进一个事件。

内容类型：narration（旁白）、dialogue（台词）、action（动作）。台词和动作使用稳定 speaker 标识 player / character，角色名仅用于显示。

角色气泡在左、用户气泡在右；旁白单独排版。AI 代写的用户内容用不干扰阅读的“AI-assisted”提示区分，用户自己输入的内容保留来源标记。

默认每个内容块按阅读节奏自动逐句出现，建议每块间隔 1.5–4 秒并按长度调节；可随时暂停或切到点击 Next 手动推进。减少动态效果模式默认手动推进；自动播放只展示已保存内容，不自动发起无限续写。支持暂停、显示全部、键盘操作，遵循减少动态效果偏好。离开页面停止播放，恢复时从保存的阅读位置继续。

一段完整生成、校验并保存后，再逐条展示。第一版不展示未校验的流式 JSON。阅读到段末前不显示后面的选择，避免剧透。

段末有三种状态：

- continue：普通停顿，用户可“继续剧情”或自由输入。
- decision：需要用户决定，禁用普通继续；用户必须选择意图或自由输入。不能自动代选。
- ending：故事完成，展示结尾与“重新开始”；原故事保留。

## 6. AI 代写边界：本功能最重要的规则

| 内容 | AI 是否可代写 |
| --- | --- |
| 打招呼、问近况、观察天气、接续已表达的话题 | 可以 |
| 看向窗外、拿起书等低影响动作 | 可以 |
| 落实用户刚选定的意图 | 可以，但不得扩大授权范围 |
| 表白、接受追求、确定关系、分手、排他承诺 | 必须先交给用户 |
| 接受重要身体接触或其他涉及明确同意的行为 | 必须先交给用户 |
| 透露重大秘密、承诺付款、搬迁、牺牲重要事物、危险行动 | 必须先交给用户 |
| 确定用户的核心信念、强烈爱恨、重大真实经历 | 不得凭空代写为事实 |

模型必须在重大行动发生之前停下，不能先写“你答应了”，再问用户是否同意。角色可以提议、拒绝、犹豫和反对，用户选择不等于角色一定服从。

例：用户选择“询问他是否愿意谈谈当年发生的事”，AI 可以写对应问句；不能继续替用户原谅对方、确认恋爱关系。

决策选项表达简短意图，如“试着询问原因”“暂时换个话题”“坦诚表达不满”。不同选项应带来可辨认的反应或事件变化，不做三个意思相同的选项，也不预告隐藏结局。

自由输入始终可用。输入既可为原话，也可为动作或导演指令，例如“我说：好久不见”“我先离开书店”“节奏慢一点，先不要发展感情”。上下文不明确且会涉及重大决定时，下一段先澄清，不能擅自猜测。用户明确输入的重要决定可以执行。

每段最多一个主要决策；没有重要转折时允许 continue，不强行每几句弹出选项。未处理的重大决策不得被下一段绕过。

## 7. 中途接话、重写与撤回

用户在本段尚未展示完时接话：立即暂停展示，只以已经显示的内容作为既定历史；未显示的后缀从有效时间线中移除。撤销该后缀衍生的决策与状态，再根据用户输入生成新的后续。可以保留旧版本作内部记录，但不得继续进入上下文。

这要求每块具有稳定 ID，并保存阅读位置；故事状态须能从有效前缀重建。为降低复杂度，本版不做逐块模型状态增量，可根据固定背景、已显示块和最近摘要重新构建生成上下文。

“重写本段”支持一句调整要求，使用该段开始前的检查点生成替代版本。旧段保留到替代成功保存才失效；失败可继续读旧段。只允许重写最新段，避免连带修改整个历史。

“撤回最近决定”恢复到该决策出现时的状态，后续内容退出有效时间线。不能只改选择文字而保留原来的后果。

继续、重写和提交选择互斥；请求进行中锁定相关按钮。取消生成不得提交半段内容。

## 8. 连续性、记忆与结束

每个故事独立保存地点、时间、已确认事实、用户已作决定、未解决事件和简短剧情摘要。摘要只概括有效时间线，不得把未选择选项当作已发生事实。

上下文由角色快照、场景设置、持久约束、近期有效内容、已确认决定与较早摘要组成。超长时先压缩较早叙事，保留角色核心、约束和重大决定。原文不删除。

生成内容只能写入故事记录。AI 代写的用户台词不代表用户真实偏好，不进入用户画像或长期记忆；“故事里搬家”不代表现实中搬家。不同角色、不同故事之间不互相引用。

用户可以随时“结束故事”，模型以当前事实写一个简短收束，不新增需要用户授权的重大行动。收束失败时保留现有内容，允许直接结束。完成后只读，重新开始创建新故事。

## 9. 剧情与聊天卡片数据契约

Story：id、character_id、origin_conversation_id、creation_request_id、title、character_snapshot、player_name、setup、constraints、language、status、revision、active_segment_id、created_at、updated_at。

StorySegment：id、story_id、parent_segment_id、revision、input_event、blocks、ending、summary、confirmed_facts、checkpoint、is_active。

StoryBlock：id、type、speaker、text、source（ai / user）。非台词也须明确动作归属；旁白 speaker 为空。

Decision：id、question、options[{id, intent}]、selected_option_id、custom_input、resolved_at。Decision 绑定 segment，不接受客户端自行构造其他选项。

ReadingProgress：story_id、segment_id、last_revealed_block_id。阅读进度与模型事实分开管理。

GenerationRequest：request_id、story_id、expected_revision、operation、status、result_segment_id。request_id 用于幂等；revision 防止两个页面同时追加不同后续。

ChatEvent：id、conversation_id、kind=story_card、story_id（可空以保留删除占位）、created_at、order_key、fallback_title。事件不含模型台词，不写入 Message 的 user/assistant role。可以按现有数据库习惯合并部分对象；不为此引入新数据库。

模型返回示例（ID 由服务端生成，以下为便于说明的占位值）：

```json
{
  "blocks": [
    {"type":"narration","speaker":null,"text":"雨水沿书店的玻璃缓缓滑落。"},
    {"type":"dialogue","speaker":"character","text":"没想到会在这里遇见你。"},
    {"type":"dialogue","speaker":"player","text":"是啊，好久不见。"},
    {"type":"dialogue","speaker":"character","text":"当年的事……你愿意听我解释吗？"}
  ],
  "ending": {
    "type":"decision",
    "question":"你想怎样回应？",
    "options":[{"id":"a","intent":"先听听他的解释"},{"id":"b","intent":"告诉他自己还没有准备好"}]
  },
  "summary":"两人在雨夜的书店重逢，对方提出解释往事；用户尚未决定。",
  "confirmed_facts":["地点是书店","双方多年未见"]
}
```

continue / ending 不带 options；decision 必须有 2–3 个非空不同选项。输出对象执行严格 schema 校验，限制块数量、文本长度和允许字段，speaker 只能引用本故事人物。所有文字按文本转义渲染，模型输出不能作为 HTML 执行。

## 10. 服务与生成流程

复用现有模型服务和服务端密钥管理；为故事新增独立的生成指令和解析器。首版继续使用当前文字模型，不把功能交付绑定到新的供应商。

建议操作：getConversationTimeline、createStory、listStories、getStory、generateNextSegment、submitDecision、interject、rewriteLatestSegment、undoLastDecision、saveReadingProgress、endStory。映射到项目现有 API 风格，不要求固定 URL。

一次生成的顺序：资源存在性和故事/角色关联检查（当前无账户鉴权） → 校验输入及 expected_revision → 获取请求锁和幂等记录 → 构建有效上下文 → 调用模型 → schema 与语义检查 → 原子保存内容和 revision → 返回 → 前端播放。

格式错误允许最多一次有针对性的修复生成；持续失败时返回可重试错误，不存入无效内容。语义检查包括重要决定越权、未知人物、选项与正文冲突。规则与关键词不能保证识别所有语义越权；必须配合明确模型指令、受控生成长度和人工样例评估，不能宣称绝对防止。

模型生成旁白与选项使用一次调用；不要按气泡调用。摘要可以在同次结构化输出返回，较早历史压缩只在需要时触发。限制输出预算、总上下文和并发；不预生成用户没有选的分支，不后台无限续写。

用户输入与角色描述都是叙事数据，不得作为系统权限指令执行。复用当前应用的内容规则与错误呈现，密钥不进入浏览器。

## 11. 异常与边界

| 情况 | 预期行为 |
| --- | --- |
| 网络错误 / 超时 / 模型拒绝 | 保留已保存内容与用户草稿，显示简洁原因和重试；不伪装成成功生成 |
| 重复点击或响应后断网 | 相同 request_id 返回已生成结果，不重复落库 |
| 两个窗口同时续写 | revision 不符的请求提示刷新最新进度，不覆盖历史 |
| 输出格式不合法 | 有限修复，仍失败则保持原状态 |
| 角色修改 | 现有故事继续使用快照 |
| 角色删除 | 沿用当前级联删除约定：删除该角色的故事、段落、请求记录和阅读进度；删除确认文案补充说明。角色快照不用于绕过删除 |
| 存储失败 | 不把生成结果标为已保存；保留当前可读内容，允许重试保存 |
| 刷新 / 离开 | 恢复到有效段落和阅读位置，未决选择不丢失 |
| 输入过长 | 提交前显示长度提示，服务端同样校验，不静默截断 |

当前记录在本地后端 SQLite 中保存，浏览器 sessionStorage 只用于当前会话选择；剧情正文同样必须写入后端。阅读位置可写入剧情表，浏览器离开前尽力保存，无法送达时允许少量阅读位置回退。保持 loopback、本地单用户与单 worker，不承诺跨设备同步。

## 12. 验收标准

1. 新建并调整角色后，进入其聊天，点击「＋」及 Do something together，输入场景并 Send invitation；表单关闭，当前会话只新增一张正确关联角色与场景的卡片。未点击卡片前不调用剧情模型。
2. 点击 Begin 后自动生成首段，内容落实场景与原角色设定；双方台词、动作、旁白逐句出现，暂停、手动 Next、显示全部均工作。
3. 在表白、承诺、秘密披露、危险行动等评估场景中，AI 停在行动前，保留自由输入；任何重大越权样例均作为待修复缺陷。
4. 决策未解决时，不能普通继续或自动越过；用户输入其他意图后剧情能合理响应。
5. 至少两条不同选择产生可辨认的不同后果，同时遵守角色设定。
6. 中途接话后，未展示的旧内容不再出现，也不影响后续摘要或选项。
7. 重写失败保留旧版本；成功后续写只使用新版本。
8. 撤回决定后，原后果退出上下文；刷新后也保持一致。
9. 失败、重试、重复请求、多窗口并发不产生重复或覆盖。
10. 恢复故事时准确还原阅读位置、未决选择和有效剧情。
11. 故事事件与 AI 代写内容不进入普通聊天记忆或真实用户画像。
12. 返回聊天后原卡片更新状态，重新打开可恢复未决选择；切换 Conversation 不丢卡片或串场；故事删除显示占位。手机、桌面及键盘可操作，现有角色创建、编辑、头像和聊天不回归。

验证分为：状态转换与存储集成测试、模型契约异常测试、浏览器关键流程、人工叙事评估。模型至少覆盖日常、悬疑、冲突、关系升级等 12 个固定样例，记录越权、设定矛盾和选择无效问题；不以单次正常回复代替评估。

### 15.3 建议 HTTP 契约

| 方法与路径 | 行为 |
| --- | --- |
| POST /api/characters/{cid}/stories | 接收 conversation_id、request_id 与场景；校验会话属于 cid；原子创建故事、快照、卡片，返回 201 和 story/card。此时不调用模型 |
| GET /api/conversations/{conv_id}/timeline | 合并已有 Message 和 ChatEvent，按稳定 order_key 排序，返回判别类型 text/story_card；卡片状态关联 Story 实时读取 |
| GET /api/characters/{cid}/stories | 返回该角色故事摘要列表，可按 conversation_id 过滤，用于次要查找入口 |
| GET /api/stories/{sid} | 返回设置、有效内容、阅读位置、状态与 revision |
| POST /api/stories/{sid}/actions | operation=start/continue/decide/interject/rewrite/undo/end；统一幂等与冲突校验 |
| PATCH /api/stories/{sid}/progress | 更新可见块位置，校验目标属于当前有效时间线，不触发生成 |
| DELETE /api/stories/{sid} | 用户显式删除故事，清理关联记录 |

创建请求包含 request_id，需有对应创建去重记录，唯一范围为 conversation_id + request_id；保存规范化 payload 以验证同 ID 内容一致。actions 包含 request_id、expected_revision、operation，以及按类型约束的 decision_id、option_id、content、revealed_block_id 等。相同 ID 与相同 payload 返回已保存结果；相同 ID 但不同 payload 返回 409。先检查已完成幂等结果，再检查 revision，确保响应丢失后的旧 revision 重试仍能取回结果。

服务端验证 decide 对应当前未决决策，continue 不可跨过 decision，rewrite 仅针对最新段，interject 不可声称已读不存在的块。客户端阅读位置只是叙事输入，不作为安全权限依据。

复用角色级锁串行处理故事生成、头像删除和角色删除，沿用现有单 worker 限制；生成前结束不必要的读事务。保存时通过条件 UPDATE 校验 Story.revision，保证故事内容、有效 head、摘要、决策和请求结果一起提交。远程调用无法与 SQLite 原子提交：进程在模型返回后、提交前退出，重试仍可能再次计费，应在开发说明中保留这个已有架构限制。

撤回、重写和中途接话不能删除幂等记录；重试一个已经成功但后来撤回的请求，应返回其原结果与当前故事 revision，不重新把旧分支激活。

## 16. 混合聊天时间线与完整交付要求

当前 Message 只支持 user/assistant 文本；不得把 story_id 或卡片 JSON 塞进 content 后用字符串识别。新增类型明确的时间线读取接口，普通聊天仍只向 Message 写真实文本。timeline item 使用 kind=text/story_card 判别并分别渲染。已有 GET messages 和 POST messages 契约保持兼容；聊天页发送消息后重新获取 timeline，不能用旧 messages 数组替换整个时间线而导致卡片消失。

为 Message 与 ChatEvent 提供统一稳定排序：迁移为已有 Message 建立唯一递增 timeline_order，新消息和卡片在 Conversation 锁内从数据库原子分配序号，按该序号排序；不要用两张表各自 ID 或仅时间戳碰运气。迁移保留旧消息原顺序，以 created_at、id 作为历史回填的确定性次序。老 Conversation 和旧文本消息不需重建，新增列和事件表须有迁移测试。

剧情 provider 的 history 只能来自本 Story 的有效段落，不读取普通聊天 history；聊天 provider 的 history 仍只读 Message，不把卡片、未开始场景、AI 代写台词或分支摘要送入 chat_context。这样卡片出现在聊天中，但不会变成用户已在现实中经历过的事实。

### 16.1 可观测状态与请求规则

Story.status 使用 ready / generating / active / awaiting_choice / completed；生成失败通过 last_error 和可重试请求记录表达，同时保留最后有效状态。卡片与阅读器共用状态映射。first-start 的生成状态需先持久化，并通过轻量详情刷新反映到其他窗口；首次 GET 不触发模型副作用。

start 仅在没有有效首段时允许；已成功的 start 重试直接返回保存结果。服务重启后，残留 generating 请求可按本地单 worker 的启动恢复策略标记为 interrupted，回到最后有效状态，允许显式重试；不可永远显示准备中。无法提供远程调用 exactly-once 保证，可能重复计费的边界沿用第 15 节说明。

关闭页面只停止播放及客户端等待，不承诺取消已提交的同步服务端模型调用。服务端若随后成功，保存完整段落；再次点卡片读取已完成结果，不重复调用。重写或中途接话的生成失败时，旧内容及有效 head 保持原样。

### 16.2 端到端验收脚本（必须实际走通）

1. 创建人物并手动或 AI 调整其说话风格；保存后进入其聊天。
2. 点击「＋」→ Do something together，填写“我们是多年没见的朋友，在雨夜的书店重逢”，提交 Send invitation。
3. 不发生跳页；聊天出现一张场景卡片，原文可查看，未发生正文模型调用。
4. 点击 Begin，进入阅读器；一次 start 调用生成完整首段并保存，随后逐句显示原角色、用户和旁白。
5. 遇到重要选择先暂停，呈现 2–3 个意图和自由输入；选择后生成可辨认的后果，继续逐句播放。
6. 暂停并输入一句自己的台词，后续响应这句输入；未读旧后缀不再影响剧情。
7. 返回原聊天，会话与位置正确，原卡片显示 Continue/等待选择；发送普通消息后卡片仍在原位置。
8. 刷新、重启后端、重新打开卡片，恢复有效剧情与未决选择，不重复生成第一段。
9. 完成故事后卡片显示 Revisit，可完整回顾；通过「＋」再次邀请产生另一张独立卡片。
10. 用测试 provider 验证异常、去重与状态，再用已配置真实模型人工检查角色一致性、逐句可读性和重要选择边界。未做真实模型验证时必须明确记录，不能把测试文本当成实际 AI 功能完成。

交付不得停留在按钮、表单、静态卡片或示例剧情：上述从原角色到聊天卡片、正文生成、选择分支、保存和回访的完整闭环全部属于 P0。界面依然明确是虚构 AI 角色；社交措辞用于自然交互，不用于声称其为真实人类。
